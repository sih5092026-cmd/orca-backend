ORCA — ECOSYSTEM API

Complete Technical Documentation

SIH26176 — Marine EcOsystem Reasoning with Collaborative Agents (ORCA)

------------------------------------------------------------------------

1. Purpose

This document records the current ORCA Ecosystem API implementation,
including its architecture, files, datasets, variables, request/response
contract, future-date behavior, testing, problems encountered, fixes,
limitations, security considerations, and recommended next steps.

The current implementation is a working prototype. It should not be
described as a fully validated scientific decision engine.

------------------------------------------------------------------------

2. ORCA Context

ORCA is a marine intelligence and decision-support platform intended to
combine:

-   Weather Agent
-   Ocean Agent
-   Ecosystem Agent
-   Risk Agent
-   Decision Agent
-   GIS
-   PFZ
-   Tide

The Ecosystem API supplies marine biogeochemical and biological
information to the Ecosystem Agent and later to the Risk and Decision
agents.

Its purpose is to answer questions such as:

-   What is the biological state of the ocean at a location?
-   What are chlorophyll and phytoplankton conditions?
-   What are nutrient conditions?
-   What is dissolved oxygen?
-   What are pH/carbon conditions?
-   What are expected ecosystem conditions on a future date?
-   Are satellite ocean-colour observations available?

A key project requirement is future ecosystem data, so the main
ecosystem variables use Copernicus Marine forecast-capable
biogeochemistry datasets.

5. ecosystemServer.js

The server imports getEcosystemData() from ecosystem.js.

It uses:

    process.env.PORT || 3006

Middleware:

    app.use(cors());
    app.use(express.json());

Home endpoint

    GET /

It reports:

-   service name
-   running status
-   example ecosystem endpoint

Main endpoint

    GET /api/ecosystem

Required query parameters:

    latitude
    longitude
    date

Example:

    http://localhost:3006/api/ecosystem?latitude=19.076&longitude=72.8777&date=2026-09-05

Coordinate validation

Latitude must be:

    -90 <= latitude <= 90

Longitude must be:

    -180 <= longitude <= 180

Invalid latitude or longitude returns HTTP 400.

Date validation

The Express route requires the date parameter.

If it is missing, HTTP 400 is returned.

The detailed YYYY-MM-DD validation is performed in Python.

Successful response

The current HTTP response has this structure:

    {
      "success": true,
      "location": {
        "latitude": 19.076,
        "longitude": 72.8777
      },
      "request": {
        "date": "2026-09-05"
      },
      "ecosystem": {
        "...": "..."
      }
    }

Error response

If the ecosystem process fails:

    {
      "success": false,
      "error": "Failed to fetch ecosystem data",
      "message": "..."
    }

Unknown routes return:

    {
      "success": false,
      "error": "Endpoint not found"
    }

6. ecosystem.js — Node/Python Bridge

The Node.js layer loads configuration with dotenv.

Python executable:

    process.env.PYTHON_COMMAND || "python"

Python file:

    path.join(__dirname, "ecosystem.py")

The function:

    getEcosystemData(latitude, longitude, date)

creates JSON input:

    {
      "latitude": 19.076,
      "longitude": 72.8777,
      "date": "2026-09-05"
    }

It starts Python with spawn().

The Copernicus credentials are passed to Python through environment
variables rather than hard-coded in the JavaScript source.

Python stdout handling

Node:

1.  collects stdout;
2.  checks the process exit code;
3.  rejects empty output;
4.  parses stdout as JSON;
5.  rejects a returned JSON error;
6.  resolves the parsed result.

Python stderr handling

Python diagnostic errors are collected separately in stderr.

This is important because stdout is expected to contain valid JSON.

Failure cases handled by the bridge

-   Python cannot start
-   Python exits with non-zero code
-   Python returns empty output
-   Python returns invalid JSON
-   Python returns a JSON error

8. Copernicus Dataset Architecture

The implementation intentionally uses two categories of data.

Category A — Global Ocean Biogeochemistry Analysis and Forecast

These are the primary forecast-capable ecosystem datasets:

    cmems_mod_glo_bgc-pft_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-bio_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-nut_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-car_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-co2_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-optics_anfc_0.25deg_P1D-m
    cmems_mod_glo_bgc-plankton_anfc_0.25deg_P1D-m

They provide the main future ecosystem variables.

Category B — Ocean Colour observation dataset

    cmems_obs-oc_glo_bgc-transp_nrt_l3-multi-4km_P1D

It provides:

    SPM
    ZSD
    KD490

This source is observational/near-real-time, not a future forecast
source.

9. Why the anfc Datasets Matter

A major point clarified during development is that the existing:

    cmems_mod_glo_bgc-*_anfc_0.25deg_P1D-m

datasets are already the forecast-capable biogeochemistry datasets
needed by ORCA.

There is therefore no need to replace the core BGC datasets merely to
support future dates.

This was an important correction during development.

10. Common Spatial/Temporal Request

Each Copernicus request uses approximately +/- 0.25 degrees around the
requested coordinate:

    minimum_longitude = longitude - 0.25
    maximum_longitude = longitude + 0.25

    minimum_latitude = latitude - 0.25
    maximum_latitude = latitude + 0.25

Depth:

    minimum_depth = 0.4940253794193268
    maximum_depth = 0.4940253794193268

Time:

    start_datetime = requested date
    end_datetime   = requested date

The current implementation therefore targets a near-surface value for
the requested date.

------------------------------------------------------------------------

11. Dataset Fetch Function

The central helper is:

    fetch_dataset(dataset_id, variables)

It calls:

    copernicusmarine.read_dataframe(
        dataset_id=dataset_id,
        variables=variables,
        **COMMON_PARAMS
    )

Behavior:

-   None result -> empty result
-   empty DataFrame -> empty result
-   successful DataFrame -> returned
-   exception -> diagnostic printed to stderr and empty result returned

This allows individual variables to become null when a particular
dataset has no usable value.

------------------------------------------------------------------------

12. Value Extraction

The helper:

    get_value(data, variable)

checks:

1.  data exists;
2.  the object has DataFrame columns;
3.  the requested variable exists;
4.  null values are removed;
5.  the first valid value is returned as a float.

If no valid value exists, it returns:

    None

which becomes:

    null

in JSON.

Important limitation: the current code does not explicitly perform
interpolation or an explicit nearest-grid-cell calculation. It uses the
first valid DataFrame value from the requested bounding box.

14.1 Original Ocean Colour Problem

The original implementation attempted to use:

    OCEANCOLOUR_GLO_BGC_L3_NRT_009_101

as the dataset identifier.

Copernicus returned a dataset-ID error.

The problem was that the product identifier was being used where the API
expected the programming dataset identifier.

------------------------------------------------------------------------

14.2 Ocean Colour Fix

The implementation was changed to:

    cmems_obs-oc_glo_bgc-transp_nrt_l3-multi-4km_P1D

and all three variables are requested in one call:

    SPM
    ZSD
    KD490

This fixed the dataset lookup problem for locations/dates with valid
satellite observations and also reduced unnecessary remote calls.

------------------------------------------------------------------------

14.3 Ocean Colour Future-Date Rule

Ocean Colour is observational.

Therefore, for a future date:

    suspended_matter_mg_l = null
    secchi_depth_m = null
    kd490_m_inv = null
    ocean_colour_status = "forecast_unavailable"

This is intentional.

The system must not fabricate satellite forecasts.

------------------------------------------------------------------------

14.4 Ocean Colour Current/Historical Rule

For a current or historical date, the service attempts to retrieve Ocean
Colour observations.

If all three are unavailable:

    ocean_colour_status = "no_observation"

If at least one is available:

    ocean_colour_status = "observation_available"

A null does NOT mean zero.

Null can mean:

-   no observation;
-   missing observation;
-   unavailable coverage;
-   quality/cloud filtering;
-   retrieval issue.

------------------------------------------------------------------------

15. Date Handling

Python validates:

    YYYY-MM-DD

Example:

    2026-09-05

Invalid dates produce:

    Invalid date. Use YYYY-MM-DD.

The requested date is compared with the current UTC date.

The implementation classifies the request as:

    future_forecast
    current
    historical

It also calculates:

    days_from_today

Example:

If current UTC date is 2026-09-03 and requested date is 2026-09-05:

    days_from_today = 2
    forecast_status = future_forecast

23. Problems Encountered and Fixes

Problem 1 — Wrong Ocean Colour Dataset ID

Symptom

Copernicus reported that the dataset did not exist / the dataset ID was
incorrect.

Cause

A Copernicus product ID was passed instead of the programming dataset
ID.

Fix

Use:

    cmems_obs-oc_glo_bgc-transp_nrt_l3-multi-4km_P1D

Result

SPM/ZSD/KD490 can be returned when observations are available.

------------------------------------------------------------------------

Problem 2 — Need for Future Ecosystem Data

Requirement

ORCA needs future conditions for decision support.

Problem

Satellite Ocean Colour cannot be treated as a future forecast source.

Fix

Use the existing Global Ocean Biogeochemistry Analysis and Forecast anfc
datasets for the core ecosystem variables.

Result

Future requests such as 2026-09-05 return forecast ecosystem values when
coverage exists.

------------------------------------------------------------------------

Problem 3 — Future Ocean Colour Values Become Null

Observation

For future dates:

    SPM = null
    ZSD = null
    KD490 = null

Interpretation

This is correct, not a failure.

Fix/Protection

The API explicitly sets:

    ocean_colour_status = forecast_unavailable

This prevents the ORCA system from treating unavailable satellite
observations as predicted measurements.

------------------------------------------------------------------------

Problem 4 — Ocean Colour Can Be Null on Historical/Current Dates

Observation

Some dates/locations can return null SPM/ZSD/KD490.

Cause

Satellite observation coverage is not guaranteed at every location/date.

Correct interpretation

Use:

    no_observation

when all three are unavailable.

Do not replace null with zero.

------------------------------------------------------------------------

Problem 5 — Slow Response Time

Observation

An individual ecosystem request has taken roughly around 80–100 seconds
in the observed development environment.

Cause

The implementation performs multiple remote Copernicus calls
sequentially:

1.  PFT
2.  BIO
3.  Nutrients
4.  Carbon
5.  CO2
6.  Optics
7.  Plankton
8.  Ocean Colour when applicable

There is also a new Python process for each API request.

Impact

The 30-request test matrix can take a very long time.

Current optimization

SPM, ZSD and KD490 are requested together in one Ocean Colour call.

Recommended fixes

-   parallelize independent dataset requests;
-   add caching;
-   add request timeouts;
-   add retries with exponential backoff;
-   prefetch common forecast dates;
-   avoid requesting datasets that are not needed;
-   consider a persistent data service instead of spawning Python for
    every request.

------------------------------------------------------------------------

24. Copernicus Freshness Warning

During testing, Copernicus reported warnings that a dataset version was
being updated and very recent data could be not fully up to date.

This is a freshness/update warning, not automatically an API failure.

The service should eventually expose:

    source
    dataset_id
    dataset_version
    retrieved_at
    forecast_initialization_time
    forecast_valid_time
    freshness_status

This is especially important for a decision-support application.

25. Scientific/Data Interpretation Rules

ORCA must distinguish:

Forecast model data

The anfc BGC datasets provide model forecast ecosystem variables.

Satellite observation data

Ocean Colour SPM/ZSD/KD490 are observations.

Model optical attenuation

optical_attenuation_m_inv comes from the BGC optics model dataset.

Satellite KD490

kd490_m_inv comes from Ocean Colour.

These fields should not be silently treated as identical measurements.

Most importantly:

    NULL != ZERO

Null means unavailable/not applicable in the current source/query
context.

------------------------------------------------------------------------

26. Spatial Limitation

The current request uses a +/-0.25 degree bounding box and then extracts
the first valid value.

It does not currently implement:

-   explicit nearest-grid-cell selection;
-   bilinear interpolation;
-   weighted interpolation;
-   explicit application-level sea/land masking;
-   spatial quality scoring.

For the prototype this is acceptable.

For a scientifically stronger production implementation, explicit
spatial selection should be added.

------------------------------------------------------------------------

27. Depth Limitation

The current service uses a fixed near-surface depth:

    0.4940253794193268

The API does not currently support arbitrary depths such as:

    5 m
    10 m
    20 m
    50 m

It also does not provide a vertical profile.

A future Ocean/Ecosystem Agent could request multiple depths if the use
case requires them.

------------------------------------------------------------------------

28. Error Handling

Dataset level

A dataset exception is logged and the dataset result becomes empty.

Python level

Unexpected errors are returned as JSON:

    {
      "error": "..."
    }

and Python exits with a non-zero code.

Node bridge

Node handles:

-   process start failure;
-   non-zero process exit;
-   empty output;
-   invalid JSON;
-   returned JSON errors.

Express

The server converts bridge failures into HTTP 500.

This is layered error handling, but it should be strengthened with
timeout/retry logic for production.

------------------------------------------------------------------------

29. Validation Limitations

The Express layer validates coordinate ranges.

The Python layer validates the date format.

The Express layer currently checks that date exists but does not perform
the full date-format validation itself.

A future version should return a clean HTTP 400 for invalid date formats
before making a Copernicus request.

------------------------------------------------------------------------

30. Security

The .env file contains Copernicus credentials.

Those credentials must be treated as secrets.

Never:

-   commit .env to GitHub;
-   expose credentials to the frontend;
-   hard-code credentials into source files;
-   return credentials from an API response;
-   publish credentials in documentation.

Recommended .gitignore:

    .env
    .env.*
    !.env.example

Recommended example file:

    COPERNICUSMARINE_SERVICE_USERNAME=
    COPERNICUSMARINE_SERVICE_PASSWORD=
    PORT=3006
    PYTHON_COMMAND=python

If real credentials were ever committed to a public/shared repository,
rotate them.

36. Risk Agent Integration

The Risk Agent should combine ecosystem data with:

-   Weather
-   Ocean conditions
-   currents
-   waves
-   wind
-   Tide
-   GIS
-   PFZ
-   marine activity

The Ecosystem API should provide environmental evidence, not make the
final operational decision.

One variable alone should not determine risk.

2.  No application cache.
3.  No retry/backoff.

10. Ocean Colour has no future forecast source in this implementation.

15. Express validates date presence but not full date format.
16. No rate limiting.
17. No API authentication for the local service.
18. No persistent result store.

50. Final Conclusion

The ORCA Ecosystem API is currently a functional, forecast-oriented
marine ecosystem data service.

Its most important architectural decision is the separation between:

1.  forecast-capable biogeochemistry data, and
2.  observation-only Ocean Colour data.

The anfc BGC datasets provide the future ecosystem variables needed by
ORCA.

Ocean Colour remains an observation source, so future SPM/ZSD/KD490
values are explicitly marked unavailable instead of being fabricated.

The major historical integration problem was the incorrect Ocean Colour
dataset identifier. That was fixed by using the correct programming
dataset and requesting SPM, ZSD, and KD490 together.

The largest remaining engineering issue is performance because multiple
remote Copernicus requests are made sequentially and Python is spawned
for each request.

The next technical improvements should therefore focus on:

-   parallel requests;
-   caching;
-   retries/timeouts;
-   better spatial selection;
-   source/freshness metadata;
-   exposing data_info;
-   and then integrating the service with the Ecosystem, Risk, and
    Decision agents.

For the SIH26176 prototype, this implementation provides a solid
ecosystem-data foundation for the larger ORCA marine intelligence
platform.
