IMPORTANT SCOPE NOTE
--------------------
This document describes the current PFZ implementation only.

PFZ = Potential Fishing Zone.

The current implementation obtains PFZ advisory/table information from INCOIS using
Puppeteer and transforms the table into a JSON response suitable for the ORCA frontend
and future ORCA decision-support agents.

It is NOT yet a complete scientific PFZ prediction model. Several environmental fields
and scoring functions are placeholders and are listed in the "STILL LEFT" section.


1. SYSTEM OVERVIEW
==================

The PFZ service has two main files:

1. server(1).js
   - Express API server
   - Receives latitude/longitude from the client
   - Validates coordinates
   - Calls getPFZData()
   - Returns JSON

2. pfzService.js
   - Core PFZ logic
   - Detects the Indian coastal sector
   - Opens INCOIS
   - Discovers the sector SEC ID
   - Scrapes the PFZ table
   - Converts coordinates
   - Parses distance/depth ranges
   - Calculates distance from the requested location
   - Creates candidate PFZ zones
   - Selects the nearest candidate as "recommended"

Runtime:
- Node.js
- Express
- CORS
- Puppeteer Core
- Google Chrome installed locally

The API currently runs on:
http://localhost:3005


2. API ENDPOINTS
================

2.1 Health check

METHOD:
GET

URL:
http://localhost:3005/

Example:
http://localhost:3005/

Response:

{
  "success": true,
  "service": "ORCA PFZ API",
  "status": "running"
}


2.2 PFZ data endpoint

METHOD:
GET

URL:
http://localhost:3005/api/pfz

Required query parameters:
- latitude
- longitude

Example:
http://localhost:3005/api/pfz?latitude=15.49&longitude=73.83

The server converts both query parameters to JavaScript numbers:

Number(req.query.latitude)
Number(req.query.longitude)


3. INPUT VALIDATION
===================

The API now validates both numeric format and geographic coordinate limits.

Current validation:

if (
    !Number.isFinite(latitude) ||
    !Number.isFinite(longitude) ||
    latitude < -90 ||
    latitude > 90 ||
    longitude < -180 ||
    longitude > 180
) {
    return res.status(400).json({
        success: false,
        error: "Invalid latitude or longitude"
    });
}

Allowed ranges:
- Latitude: -90 to +90
- Longitude: -180 to +180

Examples:

Valid:
latitude=19.076
longitude=72.8777

Invalid:
latitude=999
longitude=72.5

Invalid:
latitude=19
longitude=999

Invalid:
latitude=abc
longitude=72.5

Expected invalid response:

HTTP 400

{
  "success": false,
  "error": "Invalid latitude or longitude"
}

This validation was added because the previous implementation accepted a finite
but geographically impossible latitude such as 999.

Text-data base URL:

======================

The service launches Chrome in headless mode.

Current launch arguments include:
- --no-sandbox
- --disable-setuid-sandbox
- --disable-dev-shm-usage

8. SEC ID DISCOVERY
===================

INCOIS uses sector IDs such as:

SEC001
SEC002
SEC003
...

The PFZ service does not permanently assume that a sector always has a specific ID.

Instead, discoverSectorIds(page) opens the INCOIS PFZ home page and reads the
available sector options.

The implementation:
1. Opens INCOIS_HOME
2. Waits for network activity to settle
3. Reads the sector <select> options
4. Normalizes sector names
5. Extracts SEC IDs from option URLs
6. Builds a mapping:

sector name -> SEC ID

Example from current testing:

GUJARAT -> SEC001
MAHARASHTRA -> SEC002
GOA -> SEC003
KARNATAKA -> SEC004
KERALA -> SEC005
SOUTH TAMILNADU -> SEC006
NORTH TAMILNADU -> SEC007
SOUTH ANDHRA PRADESH -> SEC008
NORTH ANDHRA PRADESH -> SEC009
ODISHA -> SEC010
WEST BENGAL -> SEC011
ANDAMAN -> SEC012
NICOBAR -> SEC013
LAKSHADWEEP -> SEC014

The mapping is discovered dynamically rather than being the only source of truth.


9. SECTOR PAGE FETCH
====================

After sector detection and SEC ID discovery, the service calls fetchSector().

The sector page is loaded using the SEC ID.

Conceptually:

TextData?secid=SEC_ID

Example:

https://www.incois.gov.in/MarineFisheries/TextData?secid=SEC003

The page is loaded with Puppeteer.

The service waits for:
- networkidle2
- an additional short delay

The extra wait is used because the PFZ page may need time to render its table.


10. PFZ TABLE DETECTION
=======================

The service searches the rendered page for a table whose text contains all of
these key phrases:

"from the coast"
"direction"
"bearing"
"latitude"
"longitude"

This is used to identify the PFZ advisory table rather than assuming a fixed
HTML table index.


11. TABLE ROW MAPPING
=====================

Each valid PFZ row is expected to have at least 7 columns.

The current mapping is:

Column 0:
coastal_reference

Column 1:
direction

Column 2:
bearing

Column 3:
distance range

Column 4:
depth range

Column 5:
latitude

Column 6:
longitude

Rows with fewer than 7 columns are skipped.

Header-like rows containing "from the coast" are skipped.


12. COORDINATE CONVERSION
=========================

INCOIS PFZ coordinates can be supplied in DMS format.

Example concept:

15 29 24 N
073 49 48 E

The service converts DMS to decimal degrees.

Formula:

decimal =
    degrees
    + minutes / 60
    + seconds / 3600

For S or W:
decimal = -decimal

The result is rounded to 6 decimal places.

Supported direction suffixes:
- N
- S
- E
- W

If a coordinate cannot be parsed, the row is skipped.


13. DISTANCE RANGE PARSING
==========================

The service parses textual distance ranges.

Example:

"20 - 30 km"

The parser extracts:

min = 20
max = 30

The response stores:
- distance_range_km = original/raw text
- distance_min_km = minimum numeric value
- distance_max_km = maximum numeric value

If a range cannot be parsed:
- min = null
- max = null
- raw = original text or null


14. DEPTH RANGE PARSING
=======================

Depth is processed using the same range parser.

Example:

"50 - 100 m"

The response stores:
- depth_range_m
- depth_min_m
- depth_max_m

If the range does not match the expected numeric "min - max" pattern,
min/max are null but the raw text is preserved when available.


15. BEARING
===========

Bearing is extracted from the bearing column.

Non-numeric characters are removed.

The resulting number is stored as:

bearing_deg

If the bearing cannot be converted to a finite number, it becomes null.


16. DISTANCE FROM USER
=====================

The service calculates the geographic distance between:

User location:
(userLatitude, userLongitude)

and PFZ candidate:
(latitude, longitude)

The implementation uses the Haversine formula.

Earth radius:
6371 km

Output:
distance_from_user_km

The result is rounded to 2 decimal places.

19. AVAILABLE FLAG
==================

The response contains:

available

Logic:

available = zones.length > 0

Therefore:
- true = at least one PFZ candidate was extracted
- false = no candidate zone was extracted

IMPORTANT:
available=false does not automatically mean that the location is unsafe for fishing.

It can mean:
- INCOIS has no PFZ table/candidates for the current sector
- The current advisory has no usable rows
- The parser did not find usable rows
- The location is outside the configured sectors


20. RECOMMENDED FLAG
====================

Current logic:

1. All candidate zones are sorted by distance_from_user_km.
2. The nearest candidate is assigned:

recommended = true

3. All other candidates remain:

recommended = false

IMPORTANT SCIENTIFIC LIMITATION:

"recommended" currently means:
NEAREST EXTRACTED PFZ CANDIDATE

It does NOT mean:
- highest fish probability
- highest PFZ confidence
- best SST condition
- best chlorophyll condition
- safest fishing location
- best weather
- best ocean condition
- best route

This must be improved before using the field as the final ORCA decision.

23. FORECAST DATE
=================

The service attempts to extract forecast_date from the rendered page body.

Current regular expression:

/FORECAST\s*DATE\s+(\d{1,2}\s+[A-Z]{3}\s+\d{4})/i

Expected concept:

FORECAST DATE 01 SEP 2026

The service returns the captured date if the pattern is found.

CURRENT STATUS:
forecast_date has been observed as null in the multi-location API testing.

Therefore date extraction is NOT considered complete.


24. VALID-UPTO DATE

26. LOCATION OUTSIDE CONFIGURED SECTORS
=======================================

If detectSector() returns null:

{
  "success": true,
  "location": {
    "latitude": 6.0,
    "longitude": 80.5
  },
  "pfz": {
    "available": false,
    "source": "INCOIS PFZ",
    "sector": null,
    "secid": null,
    "forecast_date": null,
    "valid_upto": null,
    "candidate_zones": [],
    "error": "Location is outside configured Indian coastal PFZ sectors."
  }
}

The HTTP request itself can still be successful because the API successfully
processed the request; "available=false" describes PFZ availability, not HTTP failure.


27. SCRAPING/PROCESSING ERROR
=============================

If the PFZ service encounters an exception, getPFZData() catches it and returns:

{
  "available": false,
  "source": "INCOIS PFZ",
  "sector": null,
  "secid": null,
  "forecast_date": null,
  "valid_upto": null,
  "candidate_zones": [],
  "error": "..."
}

At the API-server level, unexpected route errors are returned with HTTP 500.

30. INTERPRETING THE TEST RESULTS
=================================

The scraper itself is working across many sectors because it successfully:
- detects sectors
- discovers SEC IDs
- opens sector pages
- extracts PFZ tables
- generates candidate zones

A sector with zero candidates is not automatically a software bug.

For example:
- Gujarat returned no candidate rows
- South Tamil Nadu returned no candidate rows

Possible interpretation:
- the current INCOIS sector page did not provide usable PFZ rows
- the current advisory may not contain a matching table
- no PFZ candidates were available in that response

These should be distinguished from actual API errors.


31. IMPORTANT LIMITATIONS OF SECTOR DETECTION
=============================================

The sector detector is currently based on hard-coded rectangles.

It is NOT:
- coastline geometry
- marine polygon
- official administrative boundary
- EEZ geometry
- GIS point-in-polygon
- nearest coastal station calculation

Potential future improvement:
Use a proper coastal-sector geometry or a verified mapping of coastal points to
INCOIS sectors.


32. IMPORTANT LIMITATION: API DOES NOT YET FILTER PFZ CANDIDATES BY USER LOCATION
===============================================================================

The service fetches the sector's PFZ candidates and calculates the distance from
the requested location.

It does not currently appear to perform a scientific/geographic filtering step such
as:
- candidate inside a radius
- candidate inside the user's marine zone
- candidate within a selected fishing range
- candidate inside the same EEZ/territorial zone

Therefore a sector can return many candidate zones.

Example:
Maharashtra returned 100 candidates.

The frontend/decision agent will eventually need to decide how many candidates to
display or evaluate.


33. ORCA INTEGRATION
===================

The PFZ API is intended to become one input to ORCA's multi-agent decision system.

Possible ORCA flow:

User location
   |
   +--> GIS agent/service
   |
   +--> Weather agent
   |
   +--> Ocean agent
   |
   +--> Ecosystem agent
   |
   +--> PFZ data
   |
   v
Risk / Decision reasoning
   |
   v
Final fishing recommendation

PFZ should therefore provide evidence/data to the decision layer rather than being
treated as the complete final decision itself.

13. DEFENSE-IN-DEPTH VALIDATION IN pfzService.js
------------------------------------------------
The API route now validates geographic bounds.

However getPFZData() currently checks only Number.isFinite() internally.

Reason:
The service should remain safe even if it is called directly by another Node module
instead of through Express.

39. DEVELOPER HANDOFF SUMMARY
=============================

A developer receiving this API should understand:

The current PFZ API is a working INCOIS PFZ extraction service.

Input:
latitude + longitude

Processing:
1. Validate coordinates
2. Determine configured coastal sector
3. Discover INCOIS SEC ID
4. Scrape the sector PFZ table
5. Parse advisory rows
6. Convert DMS coordinates
7. Parse distance/depth
8. Calculate distance from user
9. Return candidate zones

The current implementation is therefore a strong DATA INGESTION + NORMALIZATION
layer.

It is NOT yet the final ORCA intelligence layer.

The biggest remaining work is to:
- fix advisory date extraction
- add marine environmental data
- calculate meaningful PFZ confidence/suitability
- replace nearest-only recommendation
- integrate PFZ evidence with ORCA's other agents
- improve production robustness/caching
