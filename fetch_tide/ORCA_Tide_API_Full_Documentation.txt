1. OVERVIEW
-----------

The ORCA Tide API is a Node.js/Express microservice responsible for retrieving
tide predictions for a user-selected geographic location.

The service performs four main operations:

1. Accept latitude and longitude from the client.
2. Find the nearest tide/PAT station from the local station database.
3. Request tide information from the INCOIS PAT service for that station and
   requested date range.
4. Parse and normalize the INCOIS HTML response into an ORCA-friendly JSON
   structure.

The current service runs on port 3002 by default and exposes:

    GET /

for a health check, and

    GET /tide

for tide data.

The current implementation uses:
- Node.js
- Express
- CORS
- native fetch
- Cheerio
- a local stations.json database
- INCOIS PAT tide data

The current source files are:
- tide.js
- tideService.js
- findNearestStation.js
- stations.json
- testTide.js

3. PURPOSE IN ORCA
------------------

Tide information is one component of ORCA's Ocean Agent.

The Tide API provides:
- nearest available tide station
- station coordinates
- distance from requested location
- high tide predictions
- low tide predictions
- requested date range
- source information

The Ocean Agent can later combine this information with:
- wave conditions
- wind
- sea surface temperature
- currents
- weather
- ecosystem information
- PFZ information
- risk analysis

The Tide API itself does not make the final ORCA decision.

6.1 tide.js

This is the main Express server.

Responsibilities:
- start the HTTP server
- configure CORS
- configure JSON middleware
- validate coordinates
- validate dates
- find the nearest station
- call the tide service
- build the ORCA response
- expose health and tide endpoints
- handle errors

The server defaults to port 3002.


6.2 tideService.js

This is the INCOIS integration and parsing layer.

Responsibilities:
- construct the INCOIS PAT URL
- send the HTTP request
- receive the HTML page
- locate the relevant tide table
- extract high/low tide rows
- validate tide timestamps
- parse tide heights
- remove duplicate records
- sort records chronologically
- return normalized tide data


6.3 findNearestStation.js

This is the geographic station lookup layer.

Responsibilities:
- validate numeric coordinates
- iterate through all stations
- calculate geographic distance
- select the station with the smallest distance
- return station metadata

The implementation uses the Haversine formula with Earth radius:

    R = 6371 km


6.4 stations.json

This is the local station database.

It contains station objects with:

    name
    latitude
    longitude

The current uploaded station database contains 872 lines of JSON data and
includes stations such as Chennai, Kochi, Marmagao, Mumbai-related stations,
Visakhapatnam, Port Blair, etc.

The service uses this local dataset instead of querying an external station
directory on every request.


6.5 testTide.js

It tests:

7. MAIN REQUEST FLOW
--------------------

Step 1:
Client sends latitude, longitude and date range.

Example:

    GET /tide?lat=19.076&lon=72.8777&fromDate=2026-08-29&toDate=2026-09-05

Step 2:
Express receives the request.

Step 3:
The route reads:
- lat
- lon
- fromDate
- toDate

Step 4:
Coordinates are converted to numbers.

Step 5:
Coordinates are geographically validated.

Latitude must be:

    -90 <= latitude <= 90

Longitude must be:

    -180 <= longitude <= 180

Step 6:
Dates are validated.

Expected format:

    YYYY-MM-DD

Step 7:
The service creates a location object.

Step 8:
getTideData() processes the location.

Step 9:
getTideForLocation() finds the nearest PAT station.

Step 10:
The station name is sent to INCOIS PAT.

Step 11:
INCOIS returns HTML.

Step 12:
Cheerio parses the HTML.

Step 13:
High and low tides are extracted.

Step 14:
Duplicate records are removed.

Step 15:
Records are sorted chronologically.

Step 16:
The API returns normalized JSON.

18. NEAREST STATION SEARCH
--------------------------

The station lookup receives:

    latitude
    longitude

It first verifies that both values are numeric and finite.

It then iterates over every station in stations.json.

For each station, it calculates geographic distance using the Haversine
formula.


19. HAVERSINE FORMULA
---------------------

The implementation uses:

    R = 6371 km

where R is the approximate Earth radius.

For two locations:

    latitude1, longitude1
    latitude2, longitude2

the algorithm calculates:

    dLat = latitude2 - latitude1
    dLon = longitude2 - longitude1

After conversion to radians:

    a =
        sin²(dLat/2)
        +
        cos(latitude1)
        ×
        cos(latitude2)
        ×
        sin²(dLon/2)

Then:

    c = 2 × atan2(sqrt(a), sqrt(1-a))

Distance:

    distance = R × c


20. STATION SELECTION
---------------------

The algorithm maintains:

    shortestDistance = Infinity
    nearestStation = null

For every station:

    if distance < shortestDistance

then the station becomes the current nearest station.

At the end, the nearest station is returned.


21. STATION RESPONSE
--------------------

The nearest station is normalized to:

    {
      "name": "...",
      "latitude": ...,
      "longitude": ...,
      "distance_km": ...
    }

Distance is rounded to two decimal places.

    toDate

If INCOIS responds with a non-2xx status, the service throws:

    INCOIS request failed: <status>


25. HTML PARSING
----------------

INCOIS returns an HTML page.

The service loads it with:

    cheerio.load(html)

Then it examines HTML tables.

The parser searches for a table whose text contains both:

    "high tide"

and:

    "low tide"

This avoids relying only on a fixed table index.


26. TIDE TABLE EXTRACTION
-------------------------

For each matching table, the parser examines table rows.

It extracts td elements.

The expected row structure is:

    High Time | High Level | Low Time | Low Level

Example:

    30-08-2026 00:09
    1.20
    30-08-2026 05:59
    0.36

The parser requires at least four cells.


27. HIGH TIDE PROCESSING
------------------------

The first cell is interpreted as:

    highTime

The second cell is converted to:

    highLevel

The record is accepted only when:
- highTime has the expected timestamp format
- highLevel is a finite number

The normalized record internally contains:

    date
    time
    height_m


28. LOW TIDE PROCESSING
-----------------------

The third cell is:

    lowTime

The fourth cell is:

    lowLevel

The record is accepted only when:
- lowTime has the expected timestamp format
- lowLevel is a finite number

The normalized record contains:

    date
    time
    height_m


29. TIDE TIME FORMAT
--------------------

The expected INCOIS format is:

    DD-MM-YYYY HH:mm

Example:

    30-08-2026 05:59

The parser validates this format using a regular expression.


30. DATE AND TIME EXTRACTION
----------------------------

The parser separates the date and time.

Example:

    Input:
        30-08-2026 05:59

    Date:
        30-08-2026

    Time:
        05:59


31. DUPLICATE REMOVAL
---------------------

The parser creates a unique key:

    date|time|height_m

A Map is used to remove duplicate records.

This prevents repeated rows from appearing in the final response.


32. CHRONOLOGICAL SORTING
-------------------------

After duplicate removal, high and low tide records are sorted independently.

The parser converts the INCOIS timestamp into a Date representation.

The source values are treated as Indian Standard Time (IST).

The code converts IST to UTC for sorting by subtracting:

    5 hours 30 minutes

This allows correct chronological comparison.


33. FINAL TIDE OBJECT
---------------------

The parser returns:

    {
      "current_tide_height_m": null,
      "tide_phase": null,
      "high_tide": [],
      "low_tide": [],
      "tidal_current_velocity_ms": null,
      "tidal_current_direction_deg": null
    }


34. HIGH TIDE FORMAT
--------------------

Each high tide is returned as:

54. CURRENT NULL FIELDS
-----------------------

The following fields currently return null:

    current_tide_height_m
    tide_phase
    tidal_current_velocity_ms
    tidal_current_direction_deg

These fields are part of the ORCA-normalized structure but are not currently
calculated by the parser.

They must not be interpreted as measured zero values.

null means that the value is currently unavailable/not implemented.


55. IMPORTANT DISTINCTION
-------------------------

The current API provides predicted high/low tide events.

It does NOT currently calculate:
- real-time water level
- current tidal phase
- tidal current velocity
- tidal current direction

Those require additional data or algorithms.


56. CURRENT ARCHITECTURE STRENGTHS
----------------------------------

1. Clear separation of responsibilities.
2. Local station lookup is fast and deterministic.
3. Haversine distance is appropriate for geographic nearest-station selection.
4. Geographic coordinate validation is implemented.
5. Date validation is implemented.
6. INCOIS integration is isolated in tideService.js.
7. HTML parsing is separated from Express routing.
8. Duplicate tide events are removed.
9. Tide events are sorted chronologically.
10. Multiple locations are supported at the service layer.
11. A dedicated test script exists.
12. The response is already suitable for ORCA integration.


57. CURRENT LIMITATIONS
----------------------

1. Station selection is purely nearest-distance based.
2. No maximum station distance is enforced.
3. The local station dataset may contain stations outside the immediate
   Indian coastal region.
4. The INCOIS website is an HTML source rather than a dedicated API endpoint.
5. HTML structure changes at INCOIS could break the parser.
6. There is no retry mechanism.
7. There is no request timeout shown in the current fetch implementation.
8. There is no caching layer.
9. Default dates are hard-coded.
10. Current tide height is not calculated.
11. Tide phase is not calculated.
12. Tidal current velocity is not calculated.
13. Tidal current direction is not calculated.
14. No data freshness/retrieval timestamp is included in the final response.
15. The current route exposes one location per HTTP request even though the
    service layer supports multiple locations.

60. SECURITY / ROBUSTNESS
-------------------------

Recommended production protections:

- validate every query parameter
- never trust client-provided station names
- use URL encoding through URLSearchParams/URL
- set HTTP request timeout
- limit request frequency
- avoid exposing stack traces to clients
- log external service failures internally
- validate parsed numeric values
- handle malformed INCOIS HTML safely


61. PERFORMANCE
----------------

Current nearest-station lookup has approximately:

    O(N)

complexity per location,

where N is the number of stations.

For the current station database this is acceptable.

If the station database becomes very large, spatial indexing can be introduced.

Possible future approaches:
- geohash
- R-tree
- spatial database
- PostGIS


62. RELIABILITY MODEL
---------------------

The Tide API depends on two major resources:

1. local stations.json
2. external INCOIS PAT service

If stations.json is unavailable:
    nearest-station lookup fails.

If INCOIS is unavailable:
    tide retrieval fails.

A future production implementation should distinguish:

    station lookup failure
    INCOIS network failure
    INCOIS HTTP failure
    parsing failure
    no tide data
    invalid request

    CommonJS import/export mismatch.

    module.exports = {
        findNearestStation
    };

Matching import:

    const { findNearestStation } =
        require("./findNearestStation");

71. CONCLUSION
-------------

The ORCA Tide API is a modular marine-data service that converts a geographic
request into usable tide predictions.

Its architecture separates:
- HTTP routing
- coordinate/date validation
- geographic station selection
- external INCOIS retrieval
- HTML parsing
- data normalization
- testing

The most important design decision is that the API does not send raw INCOIS
HTML to ORCA. It converts the external source into a stable internal structure
containing station information, high tides, low tides, date range, and source.

This makes the Tide API suitable as a reusable component of ORCA's Ocean Agent.

The next major development step should be to enrich the tide output with
current tide state, next high/low tide calculations, tidal range, data
freshness, reliability metadata, and activity-specific risk/suitability
information.
